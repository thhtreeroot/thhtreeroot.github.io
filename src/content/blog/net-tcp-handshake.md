## 课本版三次握手

| 步骤 | 方向 | 关键标志 | 携带 | 目的 |
| --- | --- | --- | --- | --- |
| 1 | 客户端 → 服务端 | SYN=1 | ISN_c | 我要连你，我的初始序号是 ISN_c |
| 2 | 服务端 → 客户端 | SYN=1, ACK=1 | ISN_s, ack=ISN_c+1 | 收到，我的初始序号是 ISN_s |
| 3 | 客户端 → 服务端 | ACK=1 | ack=ISN_s+1 | 收到，连接建立 |

**为什么不是两次？** 若只有两次，一个在网络里迷路很久的旧 SYN 到达服务端，服务端会单方面建立半开连接并分配资源——第三次 ACK 是客户端对「旧请求」的错乱序号做的否决。

## 真实抓一次

客户端发起：

```bash
curl -s http://203.0.113.7/ -o /dev/null
```

另一端抓包：

```bash
sudo tcpdump -i eth0 host 203.0.113.7 and port 80 -nn -S
```

典型输出：

```
14:02:31.902410 IP 10.0.0.5.52344 > 203.0.113.7.80: Flags [S],  seq 1234567890, win 64240
14:02:31.902900 IP 203.0.113.7.80 > 10.0.0.5.52344: Flags [S.], seq 987654321, ack 1234567891, win 14480
14:02:31.903100 IP 10.0.0.5.52344 > 203.0.113.7.80: Flags [.],  ack 987654322, win 64240
```

三个细节值得停下来看：

1. `Flags [S] → [S.] → [.]`：SYN、SYN/ACK、纯 ACK 的字面意思；
2. 第二次握手的 `ack = 第一次 seq + 1`：**SYN 本身消耗一个序号**——面试最容易忽略的一分；
3. `win` 逐包变化：接收窗口在实时反馈「我还吃得下多少」。

## Wireshark 的 Stream 视图

过滤器：

```
tcp.stream eq 0
```

Follow TCP Stream 会看到颜色区分的双向字节流，而三次握手那三个「无色」的控制包就排在最前面。

> 我以前的困惑：三次握手传数据吗？不传。它传的是「秩序」——序号、窗口、标志位。数据从第 4 个包才开始。
