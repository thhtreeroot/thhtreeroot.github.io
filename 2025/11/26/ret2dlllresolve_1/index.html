ret2dllresolve学习-1

发表于2025-11-26|更新于2025-11-26
|浏览量:

核心概念先行

  • 动态链接库: 代码和数据的共享库，如 libc.so.6。它们被编译为位置无关代码，意味着它们可以被加载到进程地址空间的任何位置而无需修改代码本身。

  • 全局偏移表: 位于程序的数据段，为每个被程序引用的外部函数或全局变量提供一个槽。它是重定位发生的关键数据结构。

  • 过程链接表: 位于程序的代码段，包含一小段蹦床代码。当程序调用一个共享库函数时，它实际上调用的是 PLT 中的对应条目。

  • 重定位条目: 存储在可执行文件和共享库中的元数据，明确告诉动态链接器：“在地址 X 处，你需要用符号 Y 的实际地址进行修补，修补方式为类型 Z”。

详细重定位过程（以 printf 为例）

我们将过程分为三个阶段：启动时、第一次调用时、以及后续调用时。

阶段一：程序启动与初始重定位

这一步主要解决“找到库在哪里”和“设置基本通信设施”的问题。

  • 内核加载与启动解释器

当你执行 ./program 时，内核首先检查 program 的 ELF 头，发现它需要一个动态链接器。

ELF 头中指定了动态链接器的路径，通常是 /lib64/ld-linux-x86-64.so.2。

内核将程序本身和动态链接器映射到进程的虚拟地址空间，然后将控制权交给动态链接器的入口点。此时，还没有任何共享库（如 libc.so.6）被加载。

  • 动态链接器自举

动态链接器首先进行自举：它必须在不依赖任何其他库的情况下，初始化自己所需的基本数据结构。

  • 加载依赖的共享库

动态链接器读取可执行文件的 .dynamic 段，找到其依赖的库列表。

它按照依赖关系，广度优先或深度优先地加载所有需要的共享库（如 libc.so.6, libm.so.6 等）到内存中。库的加载地址通常是随机的。

  • 符号解析与初始重定位

现在，动态链接器拥有了一个所有已加载模块（可执行文件和所有共享库）的全局符号表。

它遍历可执行文件和每个共享库中的重定位表（例如 .rela.plt, .rela.dyn）。

  • 对于 GOT 的初始填充：

在 program 的 GOT 中，有一些条目需要在启动时就解析。例如，对于全局变量，动态链接器会直接查找该变量的地址，并将其写入 GOT 的对应槽中。

然而，对于函数（如 printf），为了追求启动速度，现代系统默认采用延迟绑定。这意味着，对于函数引用，GOT 的初始值并不是 printf 的真实地址。

此时，动态链接器会将 printf 在 GOT 中的条目，初始化为指向其对应的 PLT 条目中的第二条指令的地址（我们稍后会看到为什么）。更常见的实现是，初始化为一个指向动态链接器解析例程的地址，但为了概念清晰，我们按前者描述。

至此，程序启动完成，main 函数被调用。但 printf 的地址还没有被解析。

阶段二：第一次调用 printf —— 延迟绑定的魔力

这是重定位最核心、最精妙的部分。

  • 调用 PLT 条目

你的代码 call printf 在编译后，实际上被翻译成了 call printf@plt。

printf@plt 是程序内部 PLT 段中的一个条目。它看起来像这样（x86_64 汇编）：

  • 第一次调用的执行流

jmp *GOT[n]: 这是第一次调用。如前所述，GOT[n] 指向的是下一条 push 指令。所以这个跳转实际上什么都没做，只是落到了下一条指令。

push $index: 将一个数字 index（称为重定位偏移）压入栈。这个 index 唯一地标识了 printf 在重定位表中的条目。

jmp PLT0: 跳转到公共的 PLT 入口。

PLT0 的代码：

push GOT[1]: 将另一个标识信息（通常是代表当前可执行文件或库的 link_map 结构地址）压栈。现在栈上有了 (GOT[1], index) 这两个参数。

jmp *GOT[2]: 跳转到 GOT[2] 中存储的地址，这个地址在启动时已被动态链接器初始化为其内部的符号解析函数（例如 _dl_runtime_resolve_xsave）的地址。

  • 动态链接器执行解析

控制权现在交给了动态链接器的 _dl_runtime_resolve 函数。

该函数从栈上弹出 index 和 link_map。

它使用 link_map 找到当前模块的重定位表。

使用 index 作为索引，在重定位表中找到 printf 对应的重定位条目 R_X86_64_JUMP_SLOT。

这个条目告诉链接器：“需要修改的地址是 GOT[n]”。

链接器现在开始进行符号解析：

它在全局符号表中查找字符串 “printf”。

它遍历所有已加载的库，最终在 libc.so.6 中找到 printf 的函数地址。

  • 重定位（修补 GOT）

链接器获取到 printf 在内存中的实际地址。

它执行最关键的一步：将这个实际地址写回到 program 的 GOT[n] 中。 这就是重定位——直接修改全局偏移表。

跳转到目标函数并返回

链接器然后跳转到刚刚找到的 printf 的真实地址，开始执行 printf 函数。

printf 执行完毕后，返回到你的程序中，也就是最初 call printf@plt 的下一条指令。

关键点： 至此，printf 在 GOT 中的条目已经被永久性地修补为正确的地址。

阶段三：后续所有对 printf 的调用

这个过程极其高效，因为重定位只发生一次。

  • 调用 PLT 条目

你的代码依然执行 call printf@plt。

PLT 条目的行为

printf@plt 的第一条指令：jmp *GOT[n]。

现在，GOT[n] 已经被修补为 printf 的真实地址。

因此，这条指令直接跳转到了 libc.so.6 中的 printf 函数。

push 和 jmp PLT0 这两条指令被完全跳过。

后续调用的路径变得非常短：你的代码 -> PLT的一条jmp指令 -> 真实的函数。

总结与要点

角色分离：

  • PLT 是代码，不可写。它提供了一段稳定的、可供调用的蹦床代码。

  • GOT 是数据，可写。它是重定位发生的目标，充当了 PLT 和真实函数地址之间的间接指针。

  • 延迟绑定的优势：程序启动时不需要解析所有可能用到的函数，大大加快了启动速度。只有那些实际被调用的函数才会产生解析和重定位的开销。

  • 重定位的本质：是动态链接器在运行时，根据符号名找到其在内存中的绝对地址，然后将这个地址写回 GOT 中对应的槽。这个过程将间接跳转的指针从“指向解析器”修正为“指向真实目标”。

  • 安全性：现代系统使用只读重映射来保护部分 GOT，但 JUMP_SLOT 类型的重定位需要写入，所以它所在的 GOT 部分是可写的。

  • 这个过程是 Linux 动态链接能力的基石，它优雅地平衡了代码共享、地址空间随机化和运行时性能。
